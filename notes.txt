This is one of the most important concepts in backend development.

What is a migration?

A migration is a version history of your database.

Think of it like Git commits, but for your database schema.

Without migrations

Suppose today you create:

users
- id
- name
- email

A week later you add:

password

Next week you add:

isActive

How will another developer know what changed and in what order?

They won't.

With migrations

Every schema change becomes a file.

0000_create_users.sql

↓

0001_add_password.sql

↓

0002_add_is_active.sql

↓

0003_create_jobs.sql

Anyone can recreate your database by running these migrations in order.

How Drizzle uses them

You write:

export const users = pgTable(...)

Then you run:

npm run db:generate

Drizzle compares:

Your current schema
Previous migrations

and generates SQL like:

CREATE TABLE users (
    id uuid PRIMARY KEY,
    name varchar(100),
    ...
);

This SQL is saved in the drizzle/ folder.

Then you run:

npm run db:migrate

Drizzle executes those SQL statements on Neon.

Why not just create tables manually?

You could open Neon and click "Create Table."

The problem is:

Not reproducible.
Not version controlled.
Easy to forget changes.
Impossible for teammates to sync.

Production projects almost always use migrations.

Real-world example

Imagine your app is already live.

You decide to add:

phoneNumber

You don't edit the database manually.

Instead:

Update users.ts
Run db:generate

A new migration is created:

0004_add_phone_number.sql
Run db:migrate

Now every environment (development, staging, production) gets the same change.

Workflow we'll follow
Change schema (.ts)

        ↓

db:generate
(creates SQL migration)

        ↓

Review migration

        ↓

db:migrate
(applies changes to DB)

This is the standard workflow used with Drizzle, Prisma, TypeORM, and many other ORMs.
